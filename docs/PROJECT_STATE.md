### What 4.5b delivers

`POST /api/v1/auth/refresh` and `/logout` accept the refresh token **either** from
the `garajul_meu_refresh` cookie **or** from a `{"refreshToken": "..."}` body, and
answer on whichever channel the request used. No client-type header is needed,
as specification section 14 requires: the request itself reveals how the client
works.

Login always sets the `HttpOnly` `Secure` `SameSite=Strict` cookie scoped to
`/api/v1/auth`, and additionally returns the token in the body only when the
caller sends `"refreshTokenInBody": true` — so a browser's JavaScript never sees
it, while a native client, which has no cookie jar, can ask for it. Only `/login`
needs that flag: at login the client has presented nothing yet, so the backend
cannot infer the channel. On `/refresh` and `/logout` it can, and does.

`AuthService.login` is no longer `@Transactional(readOnly = true)`: issuing a
refresh token writes a row.

Logout is idempotent — logging out twice, or with no token at all, answers 204
and clears the cookie regardless.

## How this project is built — working agreement

This is a **guided build**, not code generation. The cycle is: explain → give the
exact command or file → the developer applies it → run → verify → fix → continue.
Stop at each meaningful milestone and wait for the developer's actual output
before going further.

| Rule | Detail |
|---|---|
| Who writes files | **The developer.** Provide the exact path, whether it is new or modified, the full content, and the reasoning. Do not write source files unless explicitly asked. **Never say "replace the second test" or "change lines 22–24"** — on 2026-08-15 a replacement test landed in the wrong `describe` block, silently deleting a different test and leaving the original in place, and the suite failed for a reason that looked nothing like the cause. Whole files, or a single unambiguous line with enough surrounding text to be unmistakable. |
| This document | Maintained by the assistant, not the developer. Update it at every milestone. |
| Language | Explanations in Romanian; technical terms, code, comments and identifiers in English. |
| Verification | Read the log, not just `BUILD SUCCESS`. **Always check the total test count, and on the frontend the test-file count too** — a test lost to a bad edit leaves the build green and the number smaller, and a whole file that never reached disk removes its entire block at once. Both have now happened, on 2026-08-13 and 2026-08-14. A milestone is not done until the predicted number is the observed number. |
| Versions | Verify current documentation before giving version-specific instructions. Spring Boot 4 renamed many artifacts and packages, and most material online targets 3.x. |
| Paste fragility | Long files and nested XML have repeatedly lost lines in transit — and on 2026-08-15 a single step lost **three** files: one absent, two created but **empty**. An empty source file is valid TypeScript and raises nothing, and a file nothing imports yet raises nothing either, so neither the compiler nor the test count reveals it. **Standing procedure from 2026-08-15: after the developer applies a multi-file step, the assistant verifies on disk — existence, non-zero size, expected exports — before anything is run.** It costs seconds and removes the entire class of failure. If a paste fails twice on the same content, ask before switching approach. |
| Scope | Implement only V1 features from the specification. Surface any deviation and wait for approval rather than deciding alone. |

## Flyway migrations

Flyway runs at startup over the direct (non-pooled) endpoint. Migrations live in
`backend/src/main/resources/db/migration`.

| Version | File | Applied to |
|---|---|---|
| 1 | `V1__create_users_table.sql` | Neon `development`, and every Testcontainers run |
| 2 | `V2__create_verification_tokens_table.sql` | Neon `development`, and every Testcontainers run |
| 3 | `V3__create_refresh_tokens_table.sql` | Neon `development`, and every Testcontainers run |
| 4 | `V4__create_vehicles_and_registration_certificates.sql` | Neon `development` (2026-08-16), and every Testcontainers run |
| 5 | `V5__create_ocr_usage_table.sql` | every Testcontainers run; **not yet applied to Neon `development`** |

**Phase 8 needed no migration at all.** `V4` created all thirty-seven columns
while Phase 7 mapped only six of them, so the certificate's other twenty-eight
fields arrived as entity mappings and nothing else — no `V5`, no checksum risk,
nothing to apply to Neon. That was the reason for creating the whole table in
one migration, and it paid off exactly as intended.

`V1` creates `users` per specification section 10.1, with `pk_users`, a
`ck_users_preferred_language` CHECK limiting the column to `ro`/`en`, and the
unique index `ux_users_email`.

`V2` creates `verification_tokens` per section 10.10, with a
`ON DELETE CASCADE` foreign key to `users` — which is how section 24 account
deletion reaches this table — a CHECK on the three token types, and the index
`ix_verification_tokens_user_type`.

`V4` creates **both** `vehicles` (section 10.2) and `registration_certificates`
(section 10.3) in one migration, because section 9 leaves a vehicle with no
identity of its own: the certificate is the source of truth for registration
number, VIN, make and commercial description, so a `vehicles` table on its own
would hold rows nobody could name. All thirty-five certificate columns are
created now even though Phase 7 maps only four — adding a column later is a new
migration, and there is no reason to spend four of them on a schema already
known in full. `ix_vehicles_user` serves the garage listing, which runs on every
load; `ux_registration_certificates_vehicle` enforces the one-to-one rather than
trusting it; and `ux_registration_certificates_user_vin` is the section 9 rule
that one account cannot hold the same VIN twice.

**Migrations live only in `src/main/resources/db/migration`.** A copy under
`src/test/resources` makes tests pass while the application fails to start:
tests see both `target/test-classes` and `target/classes` on the classpath, but
a running application sees only the latter. This happened once, on 2026-08-13,
and was caught by `ddl-auto: validate` refusing to boot against Neon with a
missing table.

**An applied migration is never edited.** Flyway stores its checksum; changing
the file afterwards fails the next startup with a checksum mismatch. Every
schema change from here is a new `V2__`, `V3__` file.

#### Package `ro.garajulmeu.email`

`EmailProvider` (specification section 32) with `sendVerificationCode` and
`sendPasswordResetCode`, both `(recipient, code, language)`, and
`sendEmailChangeCode(recipient, newEmail, code, language)`. Separate methods
rather than one with a purpose argument: the templates say different things, and
a reader who receives the wrong wording learns something false about their
account. The email-change method takes **four** arguments because its recipient
and its subject are two different addresses — the code goes to the address on
file, and naming the requested one in the body is what lets somebody who did not
ask for the change recognise it and refuse.
`LoggingEmailProvider` writes the message to the log instead of sending it, gated
by `@ConditionalOnProperty(garajul-meu.email.provider=logging)` with **no**
`matchIfMissing`: if the property is absent there is no `EmailProvider` bean and
the application refuses to start, rather than silently writing codes to a
production log. `EmailProperties` declares the key so the IDE knows it; the
Resend API key and sender address join it later.

Only the Argon2 hash of the six-digit code is stored. Argon2 rather than a fast
hash because a six-digit code has only a million possibilities and would be
trivially reversible from a leaked database. The cost is roughly 50 ms and 16 MB
per verification, which makes rate limiting on the auth endpoints a requirement
rather than a nicety.

#### Package `ro.garajulmeu.security`

`SecurityConfig` provides two beans:

- `PasswordEncoder` — `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()`: 16 MB memory, two iterations, parallelism one, sixteen byte salt. Chosen over `Argon2Password4jPasswordEncoder` (new in Security 7) because the documentation recommends neither, and the built-in one avoids a further third-party library. **Requires BouncyCastle**, which Spring Boot's BOM does not manage, so `org.bouncycastle:bcprov-jdk18on` is pinned explicitly in `pom.xml`.
- `SecurityFilterChain` — stateless, no session; form login, HTTP Basic and Spring's logout endpoint disabled; `/actuator/health` public, everything else `authenticated()`; `ApiErrorAuthenticationEntryPoint` wired in **two** places, so a credential-less request answers 401 rather than the default 403, and every 401 carries a body.

`CorsProperties` (`garajul-meu.cors.allowed-origins`) holds the browser origins
allowed to call the API, per section 21. Exact origins only — the CORS
specification forbids pairing a wildcard with credentials, and every request
this API answers is credentialed. An empty list is valid and safe: no browser
origin is permitted and native clients, which CORS does not bind, still work.

`SecurityConfig` registers the matching `CorsConfigurationSource` on `/api/**`
and enables `.cors(...)` **first** in the chain, so a preflight — which by
definition carries no `Authorization` header — is answered rather than refused
with a 401 the browser would report as a CORS failure. It exposes
`X-Request-Id`, which is not decoration: a browser hides every cross-origin
response header from JavaScript bar a short standard set, so without that line
the correlation id never reaches the frontend and the request id on an error
screen would always be blank, wasting the whole mechanism.

`ApiErrorAuthenticationEntryPoint` answers an unauthenticated request with the
same `ApiErrorResponse` shape as everything else. It has to exist because
authentication fails inside the filter chain, before any controller, where
`@RestControllerAdvice` cannot reach. It serialises with the injected
`tools.jackson.databind.ObjectMapper` — the bean Spring MVC itself uses, not a
fresh instance — so the JSON matches every other error byte for byte, and it
reads the correlation id from the MDC exactly as `GlobalExceptionHandler` does.

JWT is handled entirely by Spring Security — no third-party library, no custom
filter:

#### Package `ro.garajulmeu.common`

| Class | Role |
|---|---|
| `RateLimiter` | The seam. One method, `tryConsume(key, policy)`, returning a boolean rather than throwing — which error code an exhausted budget produces belongs to the layer that knows what the caller was attempting |
| `InMemoryRateLimiter` | A fixed-window counter per key in a `ConcurrentHashMap`, using `compute` so two threads on one key cannot both write `count + 1`. `RequestIdFilter` (`@Order(HIGHEST_PRECEDENCE)`) gives each request a
correlation identifier, places it in the SLF4J MDC under `requestId`, returns it
in the `X-Request-Id` response header, and clears the MDC in a `finally` block
because servlet threads are pooled.

A caller-supplied `X-Request-Id` is honoured only when it is at most 64
characters of `[A-Za-z0-9._-]`; anything else is replaced with a fresh UUID.
An unvalidated header would be a log-injection vector — newlines let a caller
forge log entries and an unbounded value lets them flood log storage.

`logging.pattern.correlation` in `application.yml` fills the slot Spring Boot
reserves inside its default console pattern, so the identifier appears on every
line without replacing the standard format or losing colours. Lines produced
outside a request show `[system]`.

**Codes added beyond the section 17 examples**, for HTTP-level failures that
belong to no domain: `MALFORMED_REQUEST`, `RESOURCE_NOT_FOUND`,
`METHOD_NOT_ALLOWED`. Without them an unparseable request body would be
reported as `INTERNAL_ERROR`, blaming us for a client mistake. Section 17
explicitly allows extending the canonical catalogue.

`AuthFlowTest`, `AuthRateLimitTest` (which overrides the rate limit properties),
`AuthServiceTest`, and `RefreshTokenServiceTest`. **Ten** classes reuse an existing
context rather than adding a fifth container: `PasswordResetServiceTest` matches
`AuthServiceTest`; `UserProfileFlowTest`, `EmailChangeFlowTest`,
`AccountDeletionTest`, `VehicleReadTest`, `VehicleWriteTest`,

`BeanOverrideContextCustomizer` and dropping it would have split the context.

log proves it: none prints a Spring banner. **Matching an existing class's
annotations exactly is what keeps the container count from growing with every
new test class**, and an unused `@MockitoBean` is a legitimate way to match —
documented in the test as intentional, or the next reader deletes it as debris.

**The rate limiter is a singleton and its counters are not transactional**, so
they survive between test methods and between test classes sharing a context.
`src/test/resources/application.yml` therefore sets every limit to 10000.
Realistic limits there would make unrelated tests fail depending on the order
they happened to run in — `AuthFlowTest` alone logs in eleven times, which is
exactly how this was found.

The second test guards specification section 20. Configuration changes are
frequent and a Neon URL leaking into the test context would be invisible — tests
would pass while writing to the real database. This makes that mistake loud.

Test infrastructure: `TestcontainersConfiguration` supplies a
`PostgreSQLContainer` annotated `@ServiceConnection`, pinned to
`postgres:18.4-alpine` to match the Neon server version. `src/test/resources/application.yml`
deliberately shadows the main configuration file so `application-local.yml` can
never reach a test.

**Because it shadows rather than merges, every `@ConditionalOnProperty` seam has
to be repeated in it.** `@DefaultValue` on the properties record does not help:
it applies when the record is bound, while the condition reads the raw
environment, so an absent property means an absent bean however the default is
written. Both seams are listed there today — `email.provider: logging` and
`ocr.provider: stub`. Anything else conditioned on a property must be added at
the moment the condition is written, because the omission stays invisible until
some bean finally injects the seam, and then it fails everywhere at once.

| 2026-08-13 | Refresh tokens are hashed with **SHA-256, not Argon2** — the opposite of passwords and verification codes, for two reasons. The token holds 256 bits of entropy, so brute force from a leaked database is irrelevant. | 2026-08-13 | A `familyId` is one login on one device. Rotation keeps the family; reuse revokes it entirely; logout revokes it. Signing out on one device therefore leaves other devices signed in. |

| 2026-08-13 | Login hashes a throwaway value when the address is unknown, so a missing account costs the same as a wrong password. | 2026-08-13 | Login checks the password **before** `isEmailVerified`. The other order would tell anyone who guesses an address that it exists and is unverified, without knowing the password. As written, `EMAIL_NOT_VERIFIED` only reaches someone who has already proved they know it. |
| 2026-08-13 | `LoginResponse` returns `expiresInSeconds`, not an absolute timestamp. A phone with a wrong clock would misjudge an absolute expiry; a duration is immune to clock skew. This is also the OAuth2 convention. |
| 2026-08-13 | `LoginRequest` does **not** carry the 12-character minimum that `RegisterRequest` does. A length policy applies to new passwords; enforcing it at login would lock existing users out of their own accounts the day the policy tightens. |

That is the requirement argued from the other end: WCAG 2.5.8 asks for a 24-pixel touch target, so the unzoomed template is below it and the zoom is what carries it over — which is precisely why section 7 asks for zoom and pan instead of a responsive shrink. |
| 2026-08-16 | **The OCR allowance is metered in the database; it is not the rate limiter.** It was tempting to call section 13's "ten a day, thirty a month" two more `RateLimitProperties` policies, and that would have been wrong. `InMemoryRateLimiter` exists to make guessing expensive, and a restart forgiving somebody their failed logins costs nothing. **Each OCR request costs money at a provider**, so a restart handing every account a fresh budget is a bill, not a courtesy — and a monthly window in a `ConcurrentHashMap` would mean a process that has to live a month to count correctly and a map that grows with every user who ever appears. Hence `V5`, one row per account per day, with the month as the sum of its days so there is no second figure to keep in step. |
| 2026-08-16 | **Attempts are counted, not successes.** The provider is paid for the call rather than for the answer, so refunding a failed one would be a discount we do not receive — and it would leave the shape where a failing provider lets one account spend without limit. A caller who is *refused by the quota* has spent nothing, which is a different thing and has its own test. |
| 2026-08-16 | **The quota is read under a pessimistic lock, and today's row is created with `on conflict do nothing`.** Two requests arriving together would otherwise both read nine and both write ten, or both insert the first row of the day and have one fail on the unique index — turning an ordinary request into an internal error. Contention is only ever with the same account, so the lock costs nothing in practice. |
| 2026-08-16 | **`Unknown property 'ocr'` in Eclipse was a stale index, not a fault.** The Spring editor reads `spring-configuration-metadata.json`, which the annotation processor writes at compile time, and the project had not been rebuilt since `OcrProperties` appeared. Building produced the three expected entries. **The quick fix that offers to write the metadata by hand must still be refused** — taking it on 2026-08-15 for `cors.allowed-origins` typed the property as a `String` and produced a convincing, entirely false error about a YAML sequence. |
| 2026-08-16 | **The client's declared content type is ignored; the format is taken from the bytes.** A declaration is an assertion, not evidence — anything can claim to be a JPEG. So a PNG uploaded as `image/jpeg` reaches the provider correctly labelled, and an executable uploaded as `image/png` does not reach it at all. `OcrImage` carries the type that was actually found, and it can only be constructed by the validator, so no code path can reach a provider having skipped the check. |
| 2026-08-16 | **Dimensions are read from the image header before anything is decoded.** A few kilobytes of valid PNG can legitimately declare a canvas twenty thousand pixels a side; decoding it to find out how big it is turns the sender's file into our memory. Checked with its own test, which builds exactly that header. |
| 2026-08-16 | **`spring.servlet.multipart.max-file-size` had to be raised, or our own limit would never have been reached.** Spring Boot refuses uploads over **one megabyte** by default, so a ten-megabyte allowance would have been decoration. The container's limit sits just above ours: absurd uploads are refused before being buffered, and merely too-large ones reach the validator, which answers with the catalogue's code rather than a container error page. |
| 2026-08-16 | **The stub provider is shaped like Document AI, not like our domain.** It returns the printed code and its value as separate blocks with boxes and confidences, because that is what the real provider gives. A stub that returned finished field values would have let 9.2's mapper be written against a convenience that does not exist, and the mapper is the part that has to survive contact with a photograph. One confidence is deliberately poor for the same reason: 9.4's review states need something to show other than "everything is fine". |
| 2026-08-16 | **The mapper anchors on the printed codes, not on the Phase 8 coordinates.** Reusing the calibrated table was the obvious-looking move and would have been wrong: those coordinates describe the *blank approved template*, while the provider reports boxes on a *photograph* taken at some other angle, distance and rotation. Matching them would mean rectifying the image first — image processing nothing asks for, introducing a source of error where none exists. The printed code sits beside its value in every photograph of a certificate, however it was taken. **This places a constraint on the 9.3 adapter**: Document AI must be asked for word or line granularity, because a provider returning one block per paragraph would hand back the code and the value fused together. |
| 2026-08-16 | **The mapper proposes only values the field can actually hold.** A certificate prints `14.03.2019` and a date input wants `2019-03-14`, so a readable date is converted and an unreadable one proposes **nothing** while asking to be checked. Putting the raw text through would leave the screen holding a value it cannot display, and the person looking at an empty box with no idea why. Same for numbers: `1780 kg` is a reading of 1780, because the unit is printed on the form. |
| 2026-08-16 | **Confidence alone does not decide a field's state.** Section 13 asks for confidence *and* semantic validation, and the reason is sharp: a VIN ending in `I` can be read with total confidence and still cannot be a VIN, since I, O and Q are excluded from the alphabet precisely because they look like 1 and 0. A value that fails its own kind is marked for review however sure the provider was. |
| 2026-08-16 | **The confidence threshold is a placeholder that says so.** Section 35 calibrates it against representative samples, in the same words it uses for the template coordinates. The coordinates could be measured because the template exists; there are **no photographs of real certificates yet**, so 0.80 is a number to be replaced in 9.5 rather than a finding. |
| 2026-08-16 | **The certificate codes are written on both sides of the application with nothing linking them** — `CertificateCode` here, the field table in the frontend. Accepted duplication of the same kind as the validation bounds: both are read from section 8, and joining them would mean shipping the specification as data. Recorded rather than hidden. |
| 2026-08-16 | **The upload is validated before any allowance is spent.** Somebody who sent a broken file asked nothing of the provider and should be charged for nothing; section 13's ten a day are requests that cost money, not attempts to make one. Asserted by its own test rather than described, so swapping the two steps fails the build. |
| 2026-08-16 | **`OcrService` is deliberately not transactional.** `OcrQuota.consume` holds a pessimistic lock on the day's row, and it has to be released before the provider is called — otherwise a second request from the same account would wait for the length of an OCR round trip while holding a pooled connection. Each step owns its own transaction and the external call happens outside all of them. This is the kind of thing that looks like a missing annotation to a later reader, hence the note in the class and here. |
| 2026-08-16 | **The scan endpoint is not nested under a vehicle and saves nothing.** Section 16 calls it "Multipart OCR; no vehicle save" and section 13 requires review and correction before storage, so the answer is a proposal and the certificate's own `PATCH` remains the only way in. Asserted by counting vehicle rows after a successful scan. |
| 2026-08-16 | **Every `@ConditionalOnProperty` seam must be repeated in `src/test/resources/application.yml`, and the omission is invisible until a bean consumes it.** The OCR provider was conditioned in 9.1b and nothing injected `OcrProvider` until `OcrService` in 9.2b, at which point **136 tests failed at once** in classes with no connection to OCR — every Spring context failed to start, and the real cause was one absent property. `@DefaultValue("stub")` on the record did not save it: the record's default applies at binding, the condition reads the environment. `matchIfMissing = true` was rejected as the fix, because it would diverge from `LoggingEmailProvider` and because an application that starts quietly with no OCR provider configured is worse than one that refuses to start. |
| 2026-08-16 | **`MissingServletRequestPartException` extends `ServletException`, not `ServletRequestBindingException`.** Handling only the latter left a multipart request with no file falling through to the catch-all and answering `INTERNAL_ERROR` for something entirely the caller's doing. Both types are now named explicitly. Second time in this project that an assumption about *what extends what* would have let a client mistake be logged at ERROR — the first was `MethodArgumentTypeMismatchException` in 7.1. Read the hierarchy; do not infer it from the name. |
| 2026-08-16 | **A stub provider must return data reality could produce, not merely data of the right shape.** The first `StubOcrProvider` gave every block a tenth of the page in width, so a printed code's own box swallowed the value beside it, and stacked rows exactly one line-tolerance apart, so a value on one row answered for a code on the next. The result was `commercialDescription: "albastru"` — the colour — and a VIN carrying the colour's confidence. **The mapper was correct throughout.** Neither its unit test nor the stub could have found this: the test builds its own blocks, and the stub had no consumer. The endpoint's test was the first thing ever to put the two in series, on the first run. |
| 2026-08-16 | **An upload the container refuses answers `IMAGE_TOO_LARGE`, not a generic failure.** The code lives in the storage group of the catalogue but is not OCR-specific, and Phase 12's vehicle images will arrive on the same handler. Known and unfixed: when Tomcat aborts an oversized multipart the client may see the connection close before it can read the response — container behaviour, not ours, and the reason our own limit sits below the container's so realistic cases reach the validator instead. |
| 2026-08-16 | **`apiFetch` must not default `FormData` to JSON.** It set `Content-Type: application/json` on any body without one, which was correct for every request the application had ever made and wrong for the first multipart one: a multipart body is only readable if the header carries the boundary the browser generated when serialising it, so declaring a type would have left the backend unable to find a single part. Found while writing the OCR call, not by it failing — but it now has a test, because the failure it would cause is a 400 that looks like a bad photograph. |
| 2026-08-16 | **The three scan states are told by line style and by words, never by colour.** Solid for detected, dashed for needs review, dotted for not detected, and the state repeated in each field's accessible description. A state carried only in colour is not carried to everyone (WCAG 1.4.1), and the description is the only route by which somebody not looking at the template learns which values came from the photograph and which they typed. The tests assert the words rather than the borders, which is what makes them tests rather than screenshots. |
| 2026-08-16 | **A validation problem outranks a scan state on the same field.** One is something to fix and the other something to know, and a box can only say one thing. Without the rule the scan state would keep announcing itself over a field that will not save. |
| 2026-08-16 | **A proposal with no value never clears a field.** "Not detected" means the photograph did not show it, never "empty it" — somebody who typed their VIN and then photographed a creased certificate must keep the VIN. Asserted twice on purpose: once on `applyScan`, once through the screen, because it is exactly the behaviour a later simplification would replace with a wholesale overwrite. |
| 2026-08-16 | **The scan starts when the file is chosen, and the input is cleared afterwards.** A second button confirming what was just chosen reads as distrust, and the file dialog is already a deliberate act. Clearing the input is not tidiness: a file input fires no `change` event when the selection has not changed, so without it the same photograph could never be retried after a failed scan. |
| 2026-08-16 | **`OCR_RATE_LIMITED` does not promise tomorrow.** The backend sends one code for the daily and the monthly allowance, so "try again tomorrow" would be a lie to anyone who had exhausted the month. The wording says "for now". |
| 2026-08-16 | **A proposal's `field` is typed as a plain string on the frontend.** The backend is a separate deployment and may be a version ahead; typing it as `CertificateField` would be an assertion the compiler cannot check and would let a field this build has never heard of become an invented key in the form. It is narrowed against the field table instead, where the check is real, and an unknown name is skipped. |
